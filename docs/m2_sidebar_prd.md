## 2. 问题陈述

### A. Dashboard 空白（页面骨架正常，内容全空）

**现象（来自用户截图，已确认）**：侧边栏、4 个指标卡、2 个图表面板、最近任务表格、系统状态面板的**外框都正常渲染**；但副标题停在「加载中…」、4 个指标卡全是 `—`、成本趋势图与质量趋势图**完全空白**、最近任务表格**无数据行**、系统状态面板**空白**。

**根因（已通过读 `web/app.js` 逐行确认，非推测）**：

1. **加载态无兜底**：`loadDashboard()` 第 158 行先把 `page-subtitle` 设为「加载中…」，成功路径要到第 178 行才覆盖它。中间串联调用了 `renderCostChart` / `renderQualityChart` / `renderSystemPanel`（第 175-177 行），**这三个调用没有 try/catch**。→ 其中任何一个抛异常，副标题就**永远停在「加载中…」**，异常被静默吞掉，用户看不到任何报错。
2. **fire-and-forget**：第 181 行 `loadRecentTasks()` **没有 `await`**（它是 async 函数）。→ 它是「发了不管」的，其内部异常无人接管，表格于是停在空 `tbody`。
3. **成本图最小值塌陷**：`renderCostChart` 第 186 行 `Math.max(...daily.map(d => d.cost), 0.000001)`。当近 14 天成本**全为 0**（空库就是这么返回的）时 `max = 0.000001`，第 191 行每根柱子 `height = Math.max(Math.round(0/0.000001*100), 2) = 2`，即**只有 2% 高度**。→ 视觉上等于「完全空白」。
4. **质量图同理**：`renderQualityChart` 第 211-215 行，14 天 `avg_score` 全为 `null` → `scored` 数组为空 → 不画评分折线也不画点；`completion_rate` 全为 0 → 完成率折线全部压在 `y = 132`（画布底部）→ 视觉上像空白。
5. **没有空态表达**：**空库（0 任务）是当前真实状态**（`GET /tasks?limit=10` 实测 DB 里另有 8 条真实任务，但 Dashboard 的 `today` 口径与 `daily` 趋势均为空），页面既不区分「加载失败」也不区分「确实没数据」，用户只能看到一片空白加几个破折号。

> ⚠️ **重要澄清（避免误判）**：后端 `GET /stats/dashboard` **实测返回 200 且完全正常**（含 14 天 `daily` 数组）。空白的**根因全部在前端**，不需要改后端指标口径。

**补充事实（读代码确认）**：`switchView()` 第 140-141 行切换视图靠 `display:none` 控制，且第 142-144 行直接改副标题 —— 说明「副标题即状态指示灯」，所以副标题卡在「加载中…」对用户是强误导信号。

### B. 侧边栏 8 项灰置（点了没反应）

**现象（来自用户截图 + 读 `index.html` 确认）**：侧边栏共 8 个灰色 `disabled` 项，各带 badge：

| 截图可见项 | badge |
|---|---|
| 工作流测试 | M2 待接入 |
| 轨迹回放 | M2 待接入 |
| 知识库 | M2 待接入 |
| 内置工具 | M3 待接入 |
| MCP 集成 | M3 待接入 |
| Agent 角色 | M3 待接入 |
| 提示词工坊 | M3 待接入 |
| 评测中心 | M3 待接入 |

**根因（读代码确认）**：这 8 个 `<div class="sidebar-item disabled">` **没有 `data-view` 属性**；而点击事件绑定在第 498 行 `document.querySelectorAll(".sidebar-item[data-view]")` —— 选择器把 disabled 项**整个排除在外**。→ 它们**连点击事件都没有**，是纯装饰性占位符，用户点了必然毫无反应。

**与后端能力对照后的真实差距（已实测确认）**：

| 侧边栏项 | 后端到底有没有支撑 | 差距 |
|---|---|---|
| 工作流测试 | ✅ 有：`POST /tasks` + `GET /tasks/{id}` + `GET /tasks/{id}/stream`(SSE) | 只差前端页面 |
| 轨迹回放 | ✅ 有：`POST /tasks` + `GET /tasks/{id}/stream` + `GET /tasks/{id}` | 只差前端页面 |
| 知识库 | ✅ 有：`/knowledge/*` 全套 6 条路由 | 只差前端页面 |
| 内置工具 | ⚠️ **部分**：`POST /tools/{tool_name}/invoke` 存在，但 **`GET /tools`（工具列表）不存在 → 实测 404** | 前端页面 + **需新增 1 个只读端点** |
| 评测中心 | ✅ 有：`GET /eval` | 只差前端页面（只读） |
| MCP 集成 | ❌ **无**：无对应端点 | 后端无支撑 |
| Agent 角色 | ❌ **无**：无对应端点 | 后端无支撑 |
| 提示词工坊 | ❌ **无**：无对应端点 | 后端无支撑（提示词是 `core/llm/prompts/v1/*.md` 文件，无 HTTP 读写接口） |

**结论**：8 项里有 **5 项后端已就绪、能真跑通**（工作流测试、轨迹回放、知识库、评测中心，加上「内置工具」需补 1 个列表端点即就绪），剩余 **3 项后端确实没有**（MCP 集成、Agent 角色、提示词工坊）。本轮必须诚实区分，不能把「待接入」当成「只要写前端就行」。

### 4.2 P0 需求（Must have）

#### P0-1 修复 `loadDashboard()` 的加载态与异常兜底

**要做的事（需求描述，不含实现代码）**：
- `loadDashboard()` 的整个渲染流程（指标卡 → 两张图 → 系统面板 → 最近任务）必须被异常兜底包裹；**任一渲染环节失败，都必须把副标题从「加载中…」改写成明确的错误提示**（含失败环节名称），不得静默。
- 副标题「加载中…」只允许在**请求进行中**出现；请求结束后无论成功失败都必须被覆盖。
- 页面需要能区分并展示三种状态：**加载中 / 加载失败（含原因）/ 加载成功（含数据生成时间）**。

**验收标准**
1. 正常环境打开 `/console`，1 秒内副标题**不再是**「加载中…」，而是含 `数据生成于 HH:MM:SS` 的成功文案。
2. 人为让 `renderSystemPanel` 收到 `undefined`（把 `/stats/dashboard` 响应中的 `system` 字段临时去掉）→ 副标题显示**含错误关键字**的失败文案，**且页面上出现可见错误提示**（非静默）；副标题**绝不**停留在「加载中…」。
3. `/stats/dashboard` 返回 500 → 副标题显示 `加载失败：...`（现有逻辑保留）。
4. 断网（API 不可达）→ 副标题显示 `无法连接 API...`。

#### P0-2 修复 `loadRecentTasks()` 的 fire-and-forget 与空态

**要做的事**：
- 让 `loadRecentTasks()` 的调用被正确等待/接管，**异常必须被捕获并显示在表格内**。
- 表格空数据时显示空态文案（如「暂无任务」），与「加载失败」文案**在视觉上可区分**。

**验收标准**
1. 空库时「最近任务」表格显示空态文案（**不是**空白 `tbody`），且**不报错**。
2. 让 `/tasks?limit=10` 返回 500 → 表格内显示 `加载失败：...`（红字），页面其他区域不受影响。
3. `loadDashboard()` 结束后，「最近任务」表格的加载状态**已结束**（不残留 pending 状态）：可通过在控制台观察 network 请求完成顺序验证。

#### P0-3 成本趋势图：零值基线与空态

**要做的事**：
- 当近 14 天成本**全为 0** 时，图表必须给出**可读的基线表达**（而不是 2% 高的隐形柱子）：要么统一显示一个「零值基线」高度并配「近 14 天无花费」说明，要么在图上叠加明确的空态文案。
- 保留「今天」与「历史日期」的颜色区分与 `title` 悬浮提示。

**验收标准**
1. 空库（`daily` 全为 0）→ 成本趋势图**肉眼可见**不为空白：图上出现「近 14 天无花费」类文案，且柱子不再是 2% 高度。
2. `daily` 有数据（如某天 cost=0.5、其余 0）→ 该天柱子高度接近满高，其余天为 0 高度基线；悬浮显示 `日期：金额（N 条任务）`。
3. 14 根柱子的日期标签仍然全部可见。

#### P0-4 质量趋势图：无评分数据空态

**要做的事**：
- 当 14 天 `avg_score` 全为 `null`（无任何评分）且 `completion_rate` 全为 0 时，图表区域**必须给出明确空态文案**（如「近 14 天暂无评分数据」）。
- 折线/面积图在完成率全 0 时不应被误解为「图挂了」：需要在与空态文案配合下保持一致表达。

**验收标准**
1. 空库 → 质量趋势图区域显示空态文案；**不出现纯空白**。
2. 有评分数据 → 评分折线与完成率折线均正常绘制，`暂无评分数据` 文案消失。
3. 只有完成率没有评分 → 完成率折线正常绘制，并附「暂无评分数据」提示（两者可共存）。

#### P0-5 Dashboard 空态总兜底（全局原则）

**要做的事**：
- Dashboard 的 **4 个指标卡**在空数据时不得只显示 `—` 而无解释：至少「今日任务数」要显示 `0`（而非 `—`），`—` 仅用于**真正无意义**的指标（如「平均评分」在无评分时）。
- 「系统状态」面板必须**始终有内容**（LLM 连接 / 缓存后端 / SQLite / 计费时段），不得空白。

**验收标准**
1. 空库 → 4 个指标卡中，「今日任务数」显示 `0`、「完成率」显示 `0.0%`、「今日累计成本」显示 `¥0`；「平均评分」显示 `—` 且注明「只统计有评分的任务」（该说明文案已存在）。
2. 「系统状态」面板在空库下**有 4 行完整内容**，不为空白。
3. 全页在空库下**没有一处纯空白区域**（每个卡片/图表/面板都有文字或图形）。

#### P0-6 侧边栏「工作流测试」页（接入）

**要做的事**：
- 侧边栏移除 `disabled`、加 `data-view="workflow"`，点击进入新页面。
- 页面提供：**任务输入框**、**提交按钮**、**执行过程实时区**、**结果区**、**取消按钮**。
- 提交调 `POST /tasks`，拿到 `task_id` 后订阅 `GET /tasks/{task_id}/stream`（SSE）逐帧渲染 `snapshot`/`node`/`heartbeat`/`done`/`failed`/`canceled`。
- 样式与现有控制台一致（卡片式、浅色、左侧栏 + 右侧主区）。

**验收标准**
1. 点侧边栏「工作流测试」→ 右侧主区切换到工作流页，侧边栏该项高亮，副标题更新。
2. 输入任务并提交 → 立即（≤1s）拿到 `task_id` 并在页面显示；随后实时区依次出现 `planner`/`executor`/`reviewer` 节点输出。
3. 任务结束 → 结果区显示 `done` 的最终答案与成本/耗时；失败时显示 `error.code` + `error.message`。
4. 运行中点「取消」→ 调用 `POST /tasks/{task_id}/cancel`，页面提示「节点边界生效」，状态变为 `canceled`。
5. API 不可达 → 页面显示明确错误与提示，**不静默**（沿用现有 `apiFetch` 的报错文案）。
6. 离开该页面（切到 Dashboard）→ 不残留轮询定时器（重复进出 5 次后仍只有 1 个活跃定时器）。

#### P0-7 侧边栏「轨迹回放」页（接入）

**要做的事**：
- 侧边栏移除 `disabled`、加 `data-view="trace"`。
- 页面提供：**task_id 输入或从最近任务列表选择**；展示该任务的分节点执行轨迹（节点名、迭代轮次、每轮产出摘要）、最终答案、评分、成本、耗时、工具调用次数、错误信息。
- 数据来源：`GET /tasks/{task_id}`（状态与结果）+ `GET /tasks/{task_id}/stream`（若任务仍在运行，则实时补全轨迹）。

**验收标准**
1. 点侧边栏「轨迹回放」→ 进入页面；输入一个已存在的 `task_id` → 展示该任务的完整信息。
2. 输入不存在的 `task_id` → 显示明确的「任务不存在」提示（对应后端 404 `task_not_found`），不白屏。
3. 轨迹区至少能呈现 `planner`/`executor`/`reviewer` 三个节点的先后顺序；运行中的任务能看到节点逐步补齐。
4. 失败任务：轨迹区显示 `error.code` 与 `error.message`。

#### P0-8 侧边栏「知识库」页（接入）

**要做的事**：
- 侧边栏移除 `disabled`、加 `data-view="knowledge"`。
- 页面分三块：**索引概览**（`GET /knowledge/overview`：文档数/分块数/token 数/各状态计数/向量后端/嵌入模型/最后索引时间）、**文档列表与操作**（列表 `GET /knowledge/documents`，上传 `POST /knowledge/documents` multipart + `overwrite` 参数，删除 `DELETE /knowledge/documents/{id}`，重试 `POST /knowledge/documents/{id}/retry`）、**检索试跑**（`POST /knowledge/search`，入参 `{query, top_k, bm25_weight, vector_weight}`）。
- 检索结果展示 `SearchHitView`：`document_name` / `chunk_seq` / `start_char` / `end_char` / `text` / `bm25_score` / `vector_score` / `score`。

**验收标准**
1. 点「知识库」→ 进入页面；概览区显示真实数据（实测空库下为 `document_count: 0`、`vector_backend: sqlite-vec`、`embedding_model: bge-small-zh-v1.5`、`last_indexed_at: null`）。
2. 空库 → 文档列表显示空态文案，概览各项显示 `0`（**不是** `—` 或空白）。
3. 上传一个 `.txt`/`.md` → 列表出现该文档且状态为索引中/完成；再次上传同名文件（`overwrite=false`）→ 页面显示后端返回的冲突提示。
4. 删除文档 → 列表移除；重试按钮 → 调用 retry 端点并刷新状态。
5. 检索输入关键词 → 展示命中片段列表，每条含文档名、块序号、分数；无命中时显示空态文案（**不得**空白）。

#### P0-9 新增后端只读端点 `GET /tools`（为「内置工具」页解阻塞）

**要做的事**：
- 新增 `GET /tools`（只读），返回工具注册表中每个工具的规格：`name` / `danger_level` / `timeout` / `retry` / `parameters`（含类型、必填、默认值）/ 说明。
- 保持与现有 `load_builtin_tools()` 注册表**同源**，不得前端硬编码。

**验收标准**
1. `GET /tools` → 200，返回数组含 **恰好 6 项**：`calculator`、`code_exec`、`extract`、`file_io`、`knowledge_search`、`web_search`。
2. 每项含 `danger_level`（`calculator`/`extract`/`knowledge_search`/`web_search` = `low`；`code_exec`/`file_io` = `high`）、`timeout`、`retry`、`parameters`。
3. 端点不消耗 LLM token、不执行任何工具（纯元数据读取），响应 ≤ 100ms。
4. 已实测确认：改动前该路径返回 **404**；改动后必须为 200。

#### P0-10 侧边栏「内置工具」页（接入）

**要做的事**：
- 侧边栏移除 `disabled`、加 `data-view="tools"`。
- 页面左侧列出**从 `GET /tools` 动态获取**的工具清单（名称 + 危险级别徽标 + 超时/重试），右侧为**试跑表单**：按所选工具的 `parameters` 动态生成输入控件，提交调 `POST /tools/{tool_name}/invoke`，body 为 `{"args": {...}}`。
- 展示返回的 `status` / `result` / `duration_ms` / `hitl{required, approved, reason}`。

**验收标准**
1. 点「内置工具」→ 左侧出现 **6 个工具**（来自 `GET /tools`，**不得硬编码**）。
2. 选 `calculator` + 表达式 `1+1` → 调 `POST /tools/calculator/invoke`，body 为 `{"args":{"expression":"1+1"}}` → 页面显示成功与结果 `2`。
3. **契约守卫**：若前端把参数摊平到顶层（不加 `args` 包裹）→ 后端返回 **422**，页面必须显示可理解的校验错误提示（不得静默）。
4. 选 `code_exec`（`danger_level: high`）试跑 → 页面**先给出高危二次确认**，确认后按后端 HITL 结果如实展示（若被拒绝，显示 `hitl.required=true` 与拒绝原因，**不得**伪造成成功）。
5. `status != "success"`（如 `timeout`/`failed`）→ 页面**明确显示「执行失败」**（因为后端契约是失败也返回 HTTP 200）。
6. `danger_level: high` 的工具在列表中有**醒目的危险徽标**。

#### P0-11 侧边栏「评测中心」页（接入，只读）

**要做的事**：
- 侧边栏移除 `disabled`、加 `data-view="eval"`；badge 从「M3 待接入」中移除（本轮就接入）。
- 页面：分页表格展示 `GET /eval` 记录（含评分、等级、关联 task_id、时间），支持 `limit`（1..200，默认 50）与 `offset`，支持按 `task_id` 过滤。
- **明确不做**：本轮**不提供触发批量评测**的按钮（后端无该端点）。

**验收标准**
1. 点「评测中心」→ 进入页面；空库显示空态文案（实测 `GET /eval` 返回 `{"items":[],"total":0,...}`）。
2. 预置 3 条评测记录 → 表格显示 3 行，`total` 显示 3。
3. 分页：`limit=50` 时「下一页」按钮可用性正确；翻页调用 `offset` 生效。
4. 按 `task_id` 过滤 → 只显示该任务的记录。
5. 页面上**不存在**「运行批量评测」按钮；若有相关说明，需写明「M1 未提供该接口」。

#### P0-12 侧边栏 3 项未就绪项的诚实标注 + 交互修正

**要做的事**：
- 「MCP 集成 / Agent 角色 / 提示词工坊」保持不可进入，但：
  - badge 文案从「M3 待接入」改为 **「后端未就绪」**（不再用时间线模糊表述）；

**验收标准**
1. 点击任一未就绪项 → 出现 toast 说明原因；页面**不切换**、不报错。
2. 三项 badge 均显示「后端未就绪」。
3. 三项的视觉效果（灰、不可点光标）与可点击项可区分。
4. 侧边栏中**不存在**任何「点了毫无反应」的项 —— 要么能进页面，要么给出解释性提示。

## 6. 明确不做的事（Out of Scope）

| 不做 | 理由 |
|---|---|
| **MCP 集成页** | 后端无任何 MCP 端点（13 条 path 中不存在），做了只能是假数据。 |
| **Agent 角色页** | 后端无 agent 角色读写的 HTTP 接口；现有 `ui/pages/1_agent_manage.py` 是直连 DB 的 Streamlit 页面，不构成 API 能力。 |
| **提示词工坊页** | 后端无提示词读写接口（提示词是磁盘上的 `.md` 文件）。涉及安全与版本管理，需先定契约。 |
| **触发批量评测** | `GET /eval` 是只读的，后端未提供批量评测触发端点。 |
| **新增其余后端能力** | 本轮只允许新增 `GET /tools` 一个只读端点（P0-9），用于解阻塞「内置工具」页；不扩张到其他后端改造。 |
| **改动 `/stats/dashboard` 指标口径** | 后端该接口**实测完全正常**，问题纯在前端渲染层。改后端只会掩盖真因。 |
| **引入前端框架 / npm / 打包** | 现有 `web/` 是「零构建原生 JS」资产，且由 FastAPI 静态托管。引入构建链会破坏当前部署方式，属 M4 范畴。 |
| **Streamlit（`ui/`）与原生控制台的功能对齐** | 本轮只改 `web/`；`ui/` 保持现状。两套前端并存是既定事实，不在本轮收敛。 |
| **轨迹的原始 LLM 消息级回放** | `GET /tasks/{id}` 不含 LLM 原始消息；SSE 的 `node.update` 明确剔除 `messages`（M1 口径）。本轮只做「节点级轨迹」。 |
| **Dashboard 自动刷新 / 实时推送** | 现有 Dashboard 是一次性加载 + 手动刷新。改为轮询需先明确刷新频率与资源代价（列入待确认）。 |

## 7. 已知开放问题与后续计划

| # | 问题 | 备选方案 | 我的默认建议 |
|---|---|---|---|
| **Q1** | 「内置工具」页需要工具清单，但 `GET /tools` **实测不存在（404）**。是否允许本轮新增这一个只读端点？ | A. 新增 `GET /tools` 返回注册表元数据（只读、零 token、≤100ms）；B. 不新增，前端**硬编码** 6 个工具与参数 schema；C. 本轮「内置工具」页也不做 | **A**。硬编码（B）会让前端在后端注册表变更时开始「撒谎」，代价比一个只读端点大得多。若坚持不动后端，则接受 B 并在页面上标注「工具清单为前端静态维护」。 |

| **Q4** | 「工作流测试」页提交任务时的默认参数取什么？ | A. 全部走后端默认（不传 `max_iterations`/`review_threshold`/`run_judge`）；B. 前端给显式默认值（如 3 / 6 / false）；C. 全部暴露给用户填写 | **A + 局部 C**：默认不传走后端口径，只把 `run_judge` 做成可勾选（并提示「会多一轮 LLM 成本，且失败任务不产生评测记录」）。 |
