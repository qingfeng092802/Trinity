### 原始需求复述

补齐产品评审中「P0-3：RAG 知识库是空壳」这一核心缺口。让用户能上传文档（PDF/Markdown/Word/TXT/HTML），自动切分并向量化索引；检索层提供 BM25 + 向量的混合检索，带来源引用；把检索能力以 `knowledge_search(query, top_k)` 内置工具的形式接入 executor，使平台能回答「基于企业内部文档」的问题；控制台增加知识库管理页。**本里程碑同时是对外作品展示的关键素材：检索质量必须有可量化、可复现的评测数据（top-3 命中率），拿数字说话。**

### 目标用户取向对产品的约束（必须体现）

| 目标用户取向 | 对 PRD 的影响 |
|---|---|
| 需要可量化验证检索效果的自建 RAG 使用者 | 检索质量评测是一等公民：要有标注评测集 + 一键评测脚本 + 数字化报告，不是"感觉搜得挺准" |
| 有本地 embedding 落地经验（bge 系列 + 重排序 + BM25/向量混合检索） | 技术选型倾向**本地模型优先**（零 API 成本、可离线、链路可自主掌控）；API 方案作备选而非默认 |
| 对 API 成本敏感 | 涉及 API 成本的项必须给出估算（见 §8 Q2）；本地 embedding 方案索引成本为 **¥0** |
| 面向垂直行业知识库（如弱电 / 安防等领域语料） | 种子文档贴合该领域，与项目领域定位一致 |

## 1. 产品目标

**一句话**：M2 要解决的不是"再多个工具"，而是"Agent 睁开眼睛"——目前 executor 只能依赖模型自身知识和 5 个通用工具，无法回答任何私有文档里的问题。M2 让平台从"通用助手"变成"懂你的知识的助手"，并用评测数字证明检索是真的准。

### 4 条可量化目标

| # | 目标 | 量化标准 |
|---|---|---|
| G1 | **文档进得来**：主流格式文档可上传并完成索引，索引性能达标 | 50 页 PDF 上传后 **≤ 2 分钟**完成解析→切分→向量化→入库（本地 embedding、CPU 推理口径）；PDF/MD/DOCX/TXT/HTML 五种格式均可索引 |
| G2 | **检索得准**：混合检索质量有可量化、可复现的评测数据 | 在 ≥ 20 条人工标注 query 的评测集上（弱电种子文档），**top-3 命中率 ≥ 80%**；评测脚本一键运行并输出报告 |
| G3 | **Agent 用得上**：检索能力接入编排，全程可观测 | `knowledge_search` 注册进工具系统并被 executor 真实调用；每次调用的 query、top_k、命中 chunk 与来源引用**完整写入 trace**，轨迹回放可见 |
| G4 | **坏不了全局**：单文档失败被隔离 | 任一文档解析/切分/embedding 失败 → 该文档标记失败并给出明确错误原因，**其余文档索引与检索不受影响**；`/health` 与其他工具不受 RAG 模块故障拖累 |

## 3. 关键设计决策速览（结论先行，详细论证见 §8）

| 议题 | 决策 | 一句话理由 |
|---|---|---|
| **Embedding 默认方案** | **本地 bge-small-zh**（默认），API 为可切换备选 | 零成本、可离线、链路可自主掌控；规划文档所写"默认用 DeepSeek embedding API"疑似作者事实错误（DeepSeek 平台无官方 embedding 端点），见 Q1 |
| **混合检索** | BM25 + 向量加权融合，权重可配置（默认建议 0.4 / 0.6） | 规划文档验收要求；权重可调才能在检索测试页做对照实验 |
| **Reranker** | 不进 P0，P1（bge-reranker 本地） | 调整触发器已明确：recall@5 < 70% 才引入 Reranker；P0 先用混合检索达标 |
| **knowledge_search 安全级别** | `danger_level="low"`，**不进** HITL 高危清单 | 只读工具、无副作用，与 calculator 同级；确认性结论见 Q6 |
| **失败隔离** | 文档级隔离：索引任务逐文档独立，单文档失败只影响自身 | 与工具边界"失败编码进记录不抛异常"的既有纪律一致 |
| **检索工具入 trace** | `knowledge_search` 走既有 `ToolCallRecord` 通道，结果含来源引用 | M1 已保证工具调用全部落 trace，零额外改动即可满足验收 |

## 4. 需求池

### 4.1 P0 需求（Must have）

#### P0-1 文档上传与解析

通过 API 上传 PDF / Markdown / DOCX / TXT / HTML 文档至指定知识库，解析为纯文本。

**要求**

| 项 | 要求 |
|---|---|
| 上传方式 | `POST /knowledge/documents`（multipart 文件上传），单文件上限默认 50 MB（可配置） |
| 解析器 | PDF（文本型）、Markdown、DOCX、TXT、HTML；解析器可扩展 |
| 重复上传 | 同名文档默认拒绝（409），允许显式覆盖重传 |
| 元数据 | 记录文件名、大小、格式、上传时间、解析状态、chunk 数、Token 数 |
| 进度可查 | `GET /knowledge/documents/{id}` 返回解析/索引状态（`pending → parsing → chunking → embedding → ready / failed`） |

**验收标准**
1. 五种格式各上传一份样例文档，全部到达 `ready` 状态。
2. 50 页 PDF（文本型）从上传完成到 `ready` **≤ 2 分钟**（本地 embedding，CPU）。
3. 不支持的格式（如 .exe、图片）→ 上传即 422，错误信息列出支持的格式。
4. 同名重复上传 → 409；带覆盖参数 → 旧版本 chunk 全量清除后重建。

#### P0-2 自动切分（Chunking）

**要求**
- 按结构感知切分：Markdown/HTML 优先按标题层级，PDF/DOCX 按段落边界，最终落入 Token 窗口（`chunk_size` / `overlap` 可配置，默认值见 Q5）。
- 每个 chunk 保留元数据：来源文档 ID、chunk 序号、字符位置区间（供来源引用展示）。
- chunk_size / overlap 支持按文档级覆盖（API 参数），不满足时用全局默认。

**验收标准**
1. 一份带多级标题的 Markdown 切分后，任意 chunk 不跨标题边界（标题优先级生效的抽样验证）。
2. `chunk_size` 设为极小值（如 64）时能正常切分并索引；设为超大值时单 chunk 不超过模型上下文限制（超限有明确报错而非静默截断到坏数据）。

#### P0-3 向量化索引（Embedding + 存储）

**要求**
- Embedding 提供商抽象层（与 LLM adapter 同样的可切换思路）：默认**本地 bge-small-zh**（权重由探测脚本定位），备选 API 提供商（见 Q2），通过配置切换。
- 向量库选型见 Q3（推荐 sqlite-vec，与既有 SQLite 生态同一存储）；BM25 索引选型见 Q4。
- 索引写入既有 SQLite（或选定向量库的持久化路径），进程重启后索引**不丢**、检索**可用**（区别于 M1 队列的内存态）。
- 批量 embedding：多 chunk 批量推理，避免逐条调用；索引任务走独立执行路径（不占用 M1 任务队列的并发槽位，避免长索引饿死 Agent 任务——具体实现待定，若复用队列需评估）。

**验收标准**
1. 索引完成后重启 API 进程，检索功能立即可用（持久化验证）。
2. 50 页 PDF 约 100-150 chunks 的索引总耗时计入 G1 的 2 分钟指标。
3. 配置切换 embedding 提供商后重新索引，检索仍正常（抽象层验证）；不同提供商混存的向量给出明确策略（见 Q7）。

#### P0-4 混合检索引擎

**要求**
- BM25 关键词检索 + 向量语义检索并行执行，加权融合排序，`bm25_weight` / `vector_weight` 可配置（默认建议 0.4 / 0.6，见 Q8）。
- 检索 API：`POST /knowledge/search`，入参 `query`、`top_k`（默认 5）、权重覆盖（可选）、知识库 ID（可选，M2 单知识库时忽略）。
- 每条结果返回：chunk 原文、来源文档名、chunk 位置（序号/字符区间）、BM25 分数、向量相似度、混合总分。
- 检索为纯只读操作，目标延迟 ≤ 500ms（本地模型、百级 chunk 规模）。

**验收标准**
1. `POST /knowledge/search {"query":"六类线施工弯曲半径要求"}` → 200，返回 top_k 条带完整来源引用的结果。
2. 权重设为纯 BM25（1.0/0.0）与纯向量（0.0/1.0）分别检索，结果排序确实不同（混合生效的证明）。
3. 空 query / 超长 query → 422；知识库为空 → 200 + 空结果列表（不是报错）。

#### P0-5 检索质量评测（可量化交付的核心）

**要求**
- 建立标注评测集：基于弱电种子文档（综合布线 / 安防 / 门禁），**≥ 20 条** (query → 期望命中文档+chunk) 标注对。
- 一键评测脚本（如 `scripts/eval_retrieval.py`）：跑全部标注 query，输出 **top-3 命中率**、top-1 / recall@5、逐条命中详情，落 JSON/Markdown 报告。
- 评测可配置检索参数（权重 / top_k / 是否 Reranker），支持不同配置间对比——能讲清"我调了权重，命中率从 75% 提到 85%"。

**验收标准**
1. 默认配置下评测报告的 **top-3 命中率 ≥ 80%**（G2 达标口径）。
2. 评测脚本零 LLM 依赖（纯检索层评测，不烧 token、无 API 成本）。
3. 报告含每条 query 的命中明细，可人工复核标注质量。

#### P0-6 `knowledge_search` 内置工具

**要求**
- 新增第 6 个内置工具：`knowledge_search(query, top_k=5)`，走既有 registry 自动 Schema 生成，签名与调用契约和其余 5 个工具完全一致。
- `danger_level="low"`（只读、无副作用，见 Q6）。
- 工具结果字符串化后写入 `ToolCallRecord`，**必须携带来源引用**（文档名 + chunk 位置），从而随既有通道进入 trace——验收的"检索结果写入 trace"由此达成，无需新建 trace 机制。
- 知识库为空或检索服务不可用时，工具返回 `status="failed"` 的结构化失败记录（executor 可自我修正），**不抛异常**——与 `registry.call()` 既有契约一致。
- planner 提示词增加"是否需要检索知识库"的判断引导；executor 提示词说明如何使用检索结果与来源引用。

**验收标准**
1. 提交一条需要查知识库的任务（如"根据知识库，门禁系统常用的两种联网方式是什么"），trace 中可见 `knowledge_search` 的完整调用记录（query、结果、来源引用、耗时）。
2. `POST /tools/knowledge_search/invoke` 直接调用可用（M1 单工具通道复用验证）。
3. 知识库为空时调用 → `status="failed"` + 明确原因，任务不崩溃。
4. 不需要知识库的任务（如算术题）不被误导去检索（planner 判断逻辑抽样验证）。

#### P0-7 失败隔离与错误提示

**要求**
- 索引按文档为单位独立处理：单文档在解析/切分/embedding 任一环节失败，标记 `failed` + 结构化错误原因（哪个环节、什么异常），**不影响其他文档的索引与检索**。
- RAG 模块整体故障（如 embedding 模型加载失败）不拖垮平台主服务：`/health` 增加 RAG 状态检查项，RAG 不可用 → degraded（非 unhealthy），与 Redis 降级口径一致。
- 失败文档支持查看错误原因并一键重试索引。

**验收标准**
1. 批量上传 5 份文档，其中 1 份为损坏 PDF → 仅该文档 `failed` 且错误信息指明"PDF 解析失败"，其余 4 份 `ready` 且可检索。
2. 修复损坏文档后重试 → 该文档 `ready`。
3. 人为破坏 embedding 模型路径 → `/health` 返回 200 + degraded + RAG 检查项 fail；平台其他功能（任务提交、非检索工具）完全正常。

#### P0-8 配置扩展

新增配置全部走 `config.py`（pydantic-settings，禁止硬编码）：embedding 提供商与模型路径、chunk_size / overlap、混合检索权重、单文件大小上限、向量库路径等。默认值与 §8 拍板结果一致。

**验收标准**：通过环境变量覆盖任一项（如权重、chunk_size）后行为生效（走配置而非硬编码的证明）。

#### P0-9 测试与文档

- pytest 覆盖：解析器各格式、切分边界、检索融合排序、工具注册与调用、失败隔离（不消耗真实 LLM token；embedding 用本地小模型或测试桩）。
- `docs/m2_rag.md`：知识库使用说明（API curl 示例 + 评测脚本用法）；README 补「知识库」一节。

**验收标准**
1. `pytest tests/ -q` 全绿，新增 RAG 测试不依赖外部 API。
2. 按 `docs/m2_rag.md` 可从零复现：上传 → 索引 → 检索 → 跑评测报告。

M1 已交付独立 HTML 控制台（`web/`），M2 新增一个「知识库」页面，信息架构沿用规划文档 3.2 节的设计，收敛为三个区块：

| 区块 | 内容 |
|---|---|
| **知识库概览** | 卡片式：知识库名称、文档数、chunk 总数、Token 总量、索引状态（就绪/索引中/有失败项）、最后更新时间 |
| **文档管理** | 拖拽上传（显示解析/切分/向量化进度）；文档表格：文件名、大小、chunk 数、状态、错误原因、操作（重试/删除/详情） |
| **检索测试** | query 输入框 + top_k / 权重滑杆；结果列表：每条显示来源文档 + chunk 位置、BM25 分数、向量相似度、混合总分、chunk 原文；Reranker 开关（P1-1 后生效） |

设计约束（与 M1 同款纪律）：页面 100% 走 REST API，不做"连不上 API 就本地直跑"的降级双实现。

## 6. 明确不做的事（Out of Scope）

| 不做 | 理由 |
|---|---|
| **OCR / 扫描件 PDF 解析** | 扫描件需要 OCR 引擎（额外重依赖 + 精度问题），与"文本型 PDF 2 分钟索引"的 P0 目标正交；上传扫描件时明确报"文本层缺失，不支持" |
| **多租户 / 权限体系** | 阶段 5 明确不做（M1 已确认），M2 单用户单知识库（多知识库是 P1-3，但无权限概念） |
| **MCP 工具协议** | M3 内容 |
| **前端框架迁移** | M4 内容；M2 只在现有 HTML 控制台加页 |
| **记忆 / 会话机制 / 多轮对话式检索** | 阶段 6+；M2 的检索是单轮、无状态的 |
| **知识库在线编辑 / 协同** | 文档只进不出（上传/删除/重索引），不做内容编辑器 |
| **GraphRAG / 知识图谱检索** | 实现复杂度高，与 M2 "先把基础混合检索做准"的定位不符 |
| **分布式 / 增量向量库服务**（Milvus、Qdrant 服务端等） | 单机规模（千级 chunk）不需要独立向量服务进程 |
| **多语言切分策略** | 种子文档为中文（弱电领域），英文文档能用即可，不做分语言调优 |
| **音频 / 图片 / 视频知识源** | 超出文档知识库范畴 |

## 7. 已知限制（必须让用户知道）

| # | 限制 | 具体影响 | 缓解 |
|---|---|---|---|
| L1 | **不支持扫描件/图片型 PDF** | 无文本层的 PDF 上传即失败 | 错误信息明确提示；OCR 列为远期（见 §6） |
| L2 | **本地 embedding 的 CPU 推理速度** | bge-small-zh 在纯 CPU 上批量索引有吞吐上限，超大文档（数百页）可能超 2 分钟指标 | 2 分钟指标锚定 50 页口径；必要时提供 ONNX/量化加速（需进一步评估） |
| L3 | **embedding 提供商切换需重索引** | 不同提供商/模型的向量空间不兼容，切换后旧向量不可比 | 切换时提示全量重索引（策略见 Q7） |
| L4 | **检索质量依赖文档质量** | 结构混乱、纯表格截图、错别字多的文档命中率会下降 | 切分策略可配；评测报告的逐条明细帮助定位坏文档 |
| L5 | **检索测试页与工具调用的融合口径一致但分数展示为参考值** | BM25 与向量分数量纲不同，展示值用于相对比较而非绝对解读 | 文档说明；以混合排名与命中率为准 |

## 8. 决策记录与后续计划（附推荐与理由）

| # | 问题 | 备选方案 | 我的推荐 |
|---|---|---|---|
| **Q1** | **事实核查：DeepSeek 是否有官方 embedding API？** 规划文档写"默认用 DeepSeek embedding API"，但据我了解 DeepSeek 开放平台只有 `chat/completions` 系列端点，**没有 embedding 端点**，该处疑似作者假设错误。需核实后修正规划文档口径 | A. 确认无官方 embedding API → 修正规划文档，本地方案转正为默认；B. 核实后确有 → 重新评估 | **A**（先核实再选型；即使有 API 方案，出于成本与可控性考虑也推荐本地优先，见 Q2） |
| **Q2** | **Embedding 选型** | A. **本地 bge-small-zh**（权重由探测脚本定位）：索引/检索成本 **¥0**、可离线、1024 维中文效果好；bge-small 推理快，利于 2 分钟指标；本地模型部署与混合检索全程可调可控。B. **硅基流动 API**（BAAI/bge-m3 等）：零运维、效果略优，但引入网络依赖 + API 成本（bge-m3 有免费额度，付费模型约 ¥0.5/百万 token 量级，需按实际价格页核实；千级 chunk 索引一次性成本约几分钱，可忽略，主要是引入网络依赖且无法自主调优）。C. 其他（OpenAI text-embedding-3 等）：需海外网络 + 美元计费，不考虑 | **A（本地 bge-small-zh）**：成本 ¥0 直接命中用户成本敏感点；复用既有本地 embedding 落地经验降低实现风险；"本地部署 embedding + 自建混合检索"的可控性与可调优空间强于"调了个 API"。B 作为配置项备选保留（提供商抽象层） |
| **Q3** | **向量库选型**（单机 SQLite 生态） | A. **sqlite-vec**：SQLite 扩展，与既有 DB 同库同事务，零独立进程，备份=拷文件；生态较新但 API 简单。B. **chromadb**：嵌入式、文档成熟、开箱即用，但自带一套持久化存储 + 依赖较重，与 SQLite 形成"两套存储"。C. **FAISS**：检索性能最强，但纯内存、持久化需自管，运维成本最高 | **A（sqlite-vec）**：与"SQLite 单一存储"的项目既有哲学一致，备份/迁移最简；千级 chunk 规模下性能完全够；值得单列说明"为什么不上独立向量库"的取舍。**备选触发器**：若 sqlite-vec 与 Python 版本兼容问题导致集成受阻（需首日 spike 验证），降级到 B（chromadb） |
| **Q4** | **BM25 实现选型** | A. **rank_bm25 库**：纯 Python、简单可控、jieba 分词好接，但索引在内存、重启需重建（百级 chunk 重建毫秒级，可接受）。B. **SQLite FTS5**：持久化、与向量同库；但默认分词器对中文支持差，需 trigram 或外挂分词，中文召回质量要实测 | **A（rank_bm25 + jieba）**：中文检索质量可控（分词质量直接决定 BM25 效果），实现快、中文分词细节可调；重建成本在百级 chunk 规模下可忽略。若后续知识库规模上万 chunk 再评估 FTS5 |
| **Q5** | **chunk 策略默认值** | 推荐：`chunk_size = 500 tokens`（约 700-800 中文字符）、`overlap = 80 tokens`、Markdown/HTML 标题边界优先、段落边界次之。备选：300/50（更细粒度，利于精确问答）或 800/100（更粗，利于上下文完整） | **500 / 80**：弱电类说明文档段落普遍 300-600 字，500 能保住完整语义段；80 overlap 约覆盖一个段落交叉，成本低收益稳。最终以 Q5 实测评测集微调为准（这正是评测脚本存在的意义） |
| **Q6** | **knowledge_search 是否进 HITL 高危清单？** | 确认项：该工具只读、无副作用、无外部写入，与 calculator 同级 | **不进**：`danger_level="low"`，开启 HITL 也不拦截（HITL 只管 high）。检索可能带出私有文档内容，但 M2 是单用户本地平台，无越权场景 |
| **Q7** | **embedding 提供商切换时的向量兼容策略** | A. 切换提供商后强制全量重索引（检测到模型指纹变更即提示）；B. 支持多向量空间并存（复杂度高，不推荐） | **A**：文档表记录 embedding 模型指纹，切换后旧索引标记过期并提示重索引，简单可靠 |
| **Q8** | **混合检索默认权重** | BM25 : 向量 = 0.4 : 0.6（弱电中文文档、术语密集，向量语义主导 + BM25 精确匹配术语缩写如"POE""六类线"） | **0.4 / 0.6** 起步，可配置；用评测脚本在 3 组权重（0.3/0.7、0.4/0.6、0.5/0.5）上对比后固化默认值，报告留档 |
| **Q9** | **检索评测集规模与标注方式** | A. 20-30 条 (query → 期望命中) 标注对，人工标注（用户自标，弱电领域其本人最懂）；B. 引入 LLM Judge 自动标注（引入成本与循环论证风险） | **A**：20 条起步（≥20 达 G2 口径），人工标注保真；评测纯检索层、零 LLM 成本。后续可扩到 50 条 |

## 9. M2 出口验收清单（DoD）

沿用规划文档 4 条验收标准（可细化，不放松），逐条对应：

- [ ] **A1 索引性能**：上传一份 50 页（文本型）PDF 后，≤ 2 分钟完成索引（本地 embedding、CPU 口径；PDF/MD/DOCX/TXT/HTML 五格式均可达 ready）
- [ ] **A2 检索质量**：检索测试中，在 ≥ 20 条人工标注 query 的弱电评测集上 **top-3 命中率 ≥ 80%**；评测脚本一键运行、零 LLM 成本、报告含逐条明细
- [ ] **A3 工具集成**：`knowledge_search` 能被 executor 正确调用（含 planner 判断引导），query / top_k / 命中 chunk / 来源引用完整写入 trace，轨迹回放可查
- [ ] **A4 失败隔离**：索引失败的文档有明确错误提示（环节 + 原因），不影响其他文档索引与检索；RAG 模块整体故障时 `/health` 为 degraded 且平台其余功能正常
- [ ] 检索 API 与工具均带来源引用（文档名 + chunk 位置）
- [ ] 索引持久化：进程重启后检索立即可用
- [ ] 全部新增配置走 `config.py`，无硬编码
- [ ] `pytest tests/ -q` 全绿，RAG 测试不消耗真实 LLM token
- [ ] `docs/m2_rag.md` 可支撑从零复现全流程（上传 → 索引 → 检索 → 评测报告）
