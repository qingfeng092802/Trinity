## 3. P0：关闭四个可见边界（约 2 天）

### P0-1 修复 H-2：节点级成本累加

**根因**

`BaseNode._emit_llm_call_event()` 已经按“一次调用一条”写入 `task_events`，但节点出口的 `TraceRecord` 仍取 `last_usage`；`TaskOutcome.from_state()` 汇总的是 `TraceRecord`，所以 `tasks.cost` 只记最后一步。

**改动**

- `core/agent/base.py`
  - `__call__` 开头重置节点级累加器（token_in / token_out / cost，**不累加 duration**）；
  - `_emit_llm_call_event()` 在 **`event_sink is None` 判断之前**累加本次用量，保证批量评测（无 DB）也能得到正确 TraceRecord；
  - `_emit_trace()` 构造 `TraceRecord` 时使用累加值；`_emit_events()` 不动，避免与逐条 `llm_call` 事件重复计。
- `core/agent/executor.py`：不新增埋点，继续每步调用 `_emit_llm_call_event()`。
- 测试：新增节点内 N 次调用的用例，断言 `TraceRecord.cost == Σ usage.cost`，且 `task_events` 仍为 N 条。

**Before**

- 3 条完成态多步任务：`tasks.cost` / `Σ llm_call.cost` = 0.653 / 0.624 / 0.695（少算 30.5%~37.6%）。

**After（验收）**

- 对 `status='done'` 的上述 3 条任务重新跑真实多步任务（或走同一套 Mock 调用路径重建 TraceRecord），`/cost-breakdown` 的 `reconcile.all_equal == true`，且 `|tasks.cost - Σ llm_call.cost| <= 1e-6`；
- 取消任务 `task-1365c179c055` 不在判据内，需在关闭说明里写明原因；
- 单元测试证明不会双计：N 次调用 → TraceRecord 1 条、`task_events.llm_call` N 条、总额等于 N 次之和。

**风险**

- 累加器若只挂在 `_emit_llm_call_event` 的 sink 成功分支，无 DB 的批量评测仍会少算；必须放在 sink 判断之前。
- 不要把累加值传给 `_emit_events` 的汇总 `llm_call`，否则 executor 会双计。

### P0-4 修复 G-7：SSE 历史帧补发

**根因**

`EventBus.subscribe()` 只创建空队列；worker 在订阅前发布的事件对新连接永久缺失。`publish()` 在事件循环未绑定时还会静默丢弃，且 `_dropped_without_loop` 没有出口。

**改动**

- `api/events.py`
  - 每个活跃 `task_id` 维护有界历史 `deque(maxlen=SUBSCRIBE_QUEUE_SIZE)`，在 loop 线程的 `_fanout` 中追加；
  - `subscribe()` 创建队列后，把历史帧按序 `put_nowait`，再挂新队列；
  - 任务终态后保留 60s 再清理（兜底），不立即清空，避免“终态发布”与“新订阅”之间的竞态；另设全局清理，避免字典无限增长；
  - 补发只覆盖**已发布且仍在内存**的帧，进程重启后不补，文档里不写“无损”。
- `api/routes/tasks.py`：读取 `Last-Event-ID`，补发时跳过 `seq <= last_event_id` 的帧，避免 EventSource 自动重连重复渲染；
- 测试：
  - 事件总线单测：先发布 2 帧、再订阅、再发布 done，断言收到 2+done 且顺序正确；
  - 重连测试：带 `Last-Event-ID` 订阅，断言不回放旧帧；
  - 集成测试 `test_stream_full_sequence` 保持原断言，连续单测 20 次全绿。

**Before**

- 全量跑约 1/3 的跑次出现 `test_stream_full_sequence` 失败（`assert 1 >= 2`，planner 帧掉在订阅之前）；单跑该文件 11/11 绿。

**After（验收）**

- 事件总线单测与重连测试确定性通过；
- `test_stream_full_sequence` 单测连跑 20 次 0 失败；
- **不**以“全量 10 次全绿”作为关闭条件——G-8 是另一条独立 flake（`docs/known_residuals.md` G-8），见 §7.1。

**风险**

- 历史队列长度必须与 `SUBSCRIBE_QUEUE_SIZE` 对齐，否则补发时 `put_nowait` 会 `QueueFull`；
- 只在内存补发，不能宣称“跨重启无损”。

### P1-2 实现 `core/tools/builtin/sql_query.py`

**接口**

```python
def sql_query(
    sql: Annotated[str, Field(description="单条只读 SELECT / WITH 查询")],
    limit: Annotated[int, Field(ge=1, le=200, description="最多返回行数")] = 50,
) -> dict[str, Any]: ...
```

- 数据库路径固定在 `data/demo_sql/demo.db`，**不接受路径参数**；测试通过环境变量 `TRINITY_SQL_DEMO_DB` 覆盖；
- demo 库缺失时：注册仍成功，但工具描述标注“demo 库未初始化”；调用 raise `SqlQueryError` 并提示先运行 `python scripts/seed_demo_sql.py`，**不自动建库**；
- 工具描述在注册时读取并嵌入 demo 库的表 DDL，模型第一次调用就能看到列名；
- 注册参数：`danger_level="low"`、`timeout=5`、`retry=0`（确定性错误重试无收益）。

**安全边界（按强度从高到低）**

1. SQLite URI `mode=ro`：物理只读；
2. `Connection.set_authorizer`：只允许 `SQLITE_SELECT`、白名单表的 `SQLITE_READ`、白名单函数（count/sum/avg/min/max/round/strftime 等；如支持 `WITH RECURSIVE` 还需放行 `SQLITE_RECURSIVE`）；拒绝 `ATTACH` / `PRAGMA` / 写操作 / `sqlite_master` 读取；
3. 语句必须以 `SELECT` / `WITH` 开头，禁止分号多语句（快速失败；真正的兜底是 1 和 2）；
4. `cur.fetchmany(limit)` 取行，**不**给 SQL 拼 `LIMIT`；
5. 结果由注册表按 `RESULT_LIMIT=4000` 截断，工具自身返回 `row_count` 与 `truncated`。

**错误语义**

- 所有拒绝/数据库错误必须 **raise `SqlQueryError`**，不能返回 `{"status": "error"}`；
- 原因：`ToolRegistry.call()` 只在异常时把 `ToolCallRecord.status` 记为 `failed`；返回 error dict 会被当成成功，Reviewer 与前端都会看错；
- 异常消息附紧凑 DDL 提示，供下一轮模型改 SQL；消息本身受注册表结果长度限制。

**命名口径**

- 代码与简历统一写“关键字黑名单 + SQLite authorizer + URI 只读”，**不写 AST**；当前实现不是 AST，面试官会追问。

## 5. P2：暂缓的“多轮记忆 / 断点续跑”

原方案的模块二不是“接线”，而是三套机制从零建。当前事实：

| 缺口 | 现树读数 |
|---|---|
| checkpointer 参数 | `build_graph(..., checkpointer=...)` 存在，但 `api/runner.py` 只传 `WorkflowRunner(ctx)`，从未启用 |
| `thread_id` | `WorkflowRunner.run/stream` 的 config 没有 `thread_id`；直接挂 checkpointer 会报错 |
| SQLite 后端 | `.venv` 只有 `langgraph.checkpoint.memory`，没有 `langgraph-checkpoint-sqlite` |
| 会话字段 | `tasks` 表没有 `session_id`；需改 `storage/models.py` + `storage/migrations.py` |
| 续跑策略 | `storage/db.py::fail_interrupted_tasks()` 启动时把所有非终态任务判失败，注释写明“未自动续跑” |

结论：

- **v0.2.0 不做**；如果 JD 明确要求“多轮记忆”，单独开 **session 记忆 v1**：
  - `tasks.session_id` 迁移 + 请求字段 + Planner 注入最近 3 轮 `(query, final_answer)` + 超长摘要；
  - 明写“不支持进程重启续跑”；
  - 估算 2~3 天。
- 真正的断点续跑需要持久化队列 / lease / 启动恢复策略，另开里程碑，估算 2~4 天。
